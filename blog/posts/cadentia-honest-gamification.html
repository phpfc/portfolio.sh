Cadentia: Gamification You Can't Fake

Most gamified learning apps have the same quiet lie at their core: the points don't mean anything. You can farm them, skip past the work, or let a streak counter tick up while you learn nothing. I wanted to build the opposite — a music education platform where every coin, every badge, every level exists because someone actually practiced. Cadentia is that platform: you learn music theory, ear training, and reading in the browser, you practice piano against automatic evaluation, and the rewards you earn are provably real.

That single constraint — no status without study — turned out to shape almost every technical decision in the system. This is the story of the architecture that falls out of taking it seriously.

The Invariant That Runs Everything

Before writing a line of product code, I wrote down a set of invariants the system would hold in every phase, no exceptions. A few of them do most of the work:

  • The server is the source of truth. Data is loaded server-first through the framework's loaders and actions — never mirrored into a global client store and manually kept in sync.
  • Rewards are granted exclusively by the server. The client evaluates a performance for immediate feedback, but nothing that produces currency, XP, or progress is trusted until the server independently validates and records it.
  • The economy is an immutable ledger. From the very first coin, every transaction is an append-only row. A balance is derived, never edited.
  • No audio ML. Performance is evaluated through MIDI, not by listening. Audio is capture and playback only.

These read like principles, but they're really engineering constraints with teeth. "Rewards are granted exclusively by the server" means the client cannot be trusted to score a practice session — which means the evaluator has to exist twice, and the two copies have to agree.

Evaluating Practice Without Trusting the Client

When you play a scale on a MIDI keyboard, Cadentia needs to tell you instantly whether you nailed it — right notes, right timing. That feedback has to be immediate, so it runs in the browser. But if the browser is also the thing that decides you earned 40 coins, then a few lines of forged JSON buys you the whole economy.

So the evaluator is mirrored: the same scoring logic exists on the client (for feedback) and in the practice module on the server (for truth). The client submits the raw MIDI events it captured plus its own score. The server re-runs evaluation on those events and compares. If the numbers don't match — if a client claims 100 on a session the server scores at 53 — the submission is flagged, credited zero, and produces no progress.

// The client's self-reported score is a hint, never the truth.
const serverScore = evaluate(submission.events, exercise.expectedNotes);

if (Math.abs(serverScore - submission.clientScore) > TOLERANCE) {
  // Numbers disagree — someone's lying, or something drifted.
  await this.flag(session, { clientScore, serverScore });
  return { status: 'FLAGGED', reward: 0 };
}

// Only the server-computed result is allowed to touch the ledger.
return this.settle(session, serverScore);

To keep the two evaluators honest, they share convergence fixtures — inputs with known outputs that both implementations must produce. If someone changes the scoring rule on one side and forgets the other, the fixtures fail in CI. The mirror can't silently drift apart.

There's a nice side effect I didn't design but got for free: a plausibility floor on session duration caught a forged submission during a smoke test. A three-second "session" that claimed a full scale was rejected before evaluation even ran — the anti-forgery logic validated itself by accident.

The Economy Is a Ledger, Not a Number

The obvious way to build an in-app economy is a balance column you increment and decrement. It's also the wrong way, because the moment you can UPDATE a balance, the balance stops being trustworthy — and in a system whose entire pitch is "the rewards are real," a trustworthy balance is the product.

So there is no balance column. There's a ledger of immutable transactions, and the balance is a sum:

// Earning: a positive line, granted only by the server.
await ledger.append({
  userId,
  amount: +50,
  reason: 'NODE_MASTERED',
  // Structural idempotency: the same mastery can't pay twice.
  idempotencyKey: `node-mastered:${userId}:${nodeId}`,
});

// Spending in the shop: a negative line, under an advisory lock
// with a balance re-check inside the transaction.
await ledger.append({
  userId,
  amount: -30,
  reason: 'COSMETIC_PURCHASE',
});

// The balance is derived, never stored.
const balance = await ledger.sum(userId);

This buys real properties. Every coin is auditable back to the exact practice session that minted it. Idempotency keys make double-grants structurally impossible — mastering a node pays exactly once, no matter how many times the event is reprocessed. And when a bug once paid a bonus it shouldn't have, the fix didn't reverse the transaction; it left the erroneous line in place (the ledger is immutable) and corrected the rule going forward. The history stays honest even about its own mistakes.

Purchases race, of course — two tabs, one balance. An advisory lock per user plus a balance re-check inside the transaction guarantees exactly one of two concurrent buys succeeds, and the balance never goes negative.

Almost No Client State

The frontend is React Router 7 in framework mode — server-first by design. The rule I held to is that global client state should be roughly zero: ephemeral UI state lives in the component or in the URL, and anything the server owns is loaded through a loader, not cached in a store I have to invalidate by hand.

The one place that earns real client-side machinery is the practice session itself, and it's modeled as an explicit state machine with named states — idle → countdown → playing → evaluating → result. Using XState here isn't decoration; a practice session has genuinely illegal transitions (you can't be evaluating before you've played), and encoding them as a machine makes those bugs unrepresentable instead of merely unlikely.

// The session is a machine, not a pile of booleans.
const practiceMachine = setup({ /* ... */ }).createMachine({
  initial: 'idle',
  states: {
    idle:       { on: { START: 'countdown' } },
    countdown:  { on: { GO: 'playing' } },
    playing:    { on: { STOP: 'evaluating' } },
    evaluating: { on: { SCORED: 'result' } },
    result:     { on: { AGAIN: 'countdown', EXIT: 'idle' } },
  },
});

Two Repos, One Contract

The backend (NestJS + Prisma + PostgreSQL) and the frontend (React Router) are separate repositories, deliberately. No monorepo. The contract between them is the HTTP API, described by an OpenAPI spec that Nest generates from decorators — and the frontend's TypeScript client is generated from that spec with orval, never hand-written.

The payoff is that the contract can't quietly rot. If I remove an endpoint or change a shape on the server, regenerating the client surfaces the break at compile time on the web side. The two codebases stay in lockstep without me maintaining a shared types package by hand across a repo boundary.

It also imposes discipline I've come to appreciate: because the client is generated, the server's Swagger decorators aren't an afterthought — they are the interface. Getting the OpenAPI right is getting the frontend's types right.

Content You Can Trust, Reputation You Have to Earn

The same "no status without study" ethic extends to the library. Content lives in three tiers — golden standard, verified, and new — and promotion between tiers is a curation act, never an automatic consequence of popularity. Community appreciation is a signal that informs a curator, never a gate that admits content on its own. And you can only appreciate an exercise you've actually practiced, which keeps the signal tied to real engagement rather than drive-by voting.

Contributing content earns reputation, but reputation is kept strictly separate from currency and XP — you can't buy your way to standing, and the person who reviews their own submission earns nothing from it. Every anti-farm decision points the same direction: the numbers on your profile should mean you did the work.

What I Took From It

The interesting thing about a hard constraint is how much design it does for you. "No status without study" sounds like a product principle, but held rigorously it dictates a mirrored evaluator, an immutable ledger, server-granted rewards, and a client you assume is adversarial. I didn't set out to build all of that — I set out to make gamification that couldn't be faked, and the architecture is just what that honesty costs.

Cadentia is live at cadentia.club. If you play a scale on it and earn a coin, you can follow that coin all the way back to the exact moment your fingers hit the keys. That traceability isn't a feature bolted on top — it's the whole point.
